# 递归转发解析与来源核验

本文描述解析契约、统计口径和验证方法。账号标识、真实聊天原文、业务统计、原始载荷和采集审计仅保存在本地 `data/wecom-local/`，不纳入版本控制。来源核验、软件测试、语义推断和云端历史完整性需要分别提供证据。

## 来源证据与数据范围

每次导入需记录源数据库、快照清单、SHA-256、主群及转发子消息条数、解析缺口和媒体处理范围。原库成功解密及完整性检查可以支持本地数据核验，不能证明全部云端历史已经下载。无法证实完整历史时保留 `full_history_verified=false`。

手工录入和演示数据保持未核验来源。真实来源报告默认排除同名未核验材料，可按 `local_account` 单独查看；不能通过改写来源标记将样本认证为原库记录。未执行 OCR、语音转写或附件解包的媒体需在本地报告中列出。

交付保存在 `data/wecom-local/exports/`，快照清单、采集日志和核验结果保存在 `data/wecom-local/audits/`。需要共享真实业务数据时另行取得明确授权。

## 授权采集与原库保护

优先复用已经验证的账号 `keyring.dpapi`，避免重复探测。候选密钥在内存中验证，通过快照和 WAL 完整性校验后才保存；原始密钥不得写入报告、日志或仓库。

需要调试器采集或重新登录时，必须先说明会话中断、短暂停顿等影响并取得明确授权，由用户手动退出和重新打开客户端。硬件断点采集流程不强杀客户端、不注入 DLL、不设置软件断点；异常路径也须恢复调试状态并解除附加。采集结束后独立复核存活进程是否仍被调试。

原始 `.db`、`-wal`、`-shm` 只读复制，通过重复读取核对哈希，在副本上合并已提交 WAL 并执行 SQLite 完整性检查。每个数据库分别检查一致性，不宣称多个库之间具有全局事务一致性，不对企微原库执行 SQLite 写操作。

调试事件处理参考 [DebugActiveProcess](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-debugactiveprocess) 与 [ContinueDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent)。

## 递归解析契约

JSONL 的 `forwarded_messages`、XML 的 `recordinfo/datalist/dataitem` 与已观察到的原生 Protobuf 结构支持递归解析。容器单独保存，子消息保留自身作者、企业、时间、正文和引用，不继承转发者身份、父级时间或正文。未识别结构和损坏节点保留缺口，不能根据卡片预览补造子消息。

已观察到的原生合并转发类型为 `4`。类型 `40` 也可能表示通话，不能仅凭类型号认定为转发。以下字段布局是当前已识别结构，不保证适用于所有企微版本：

| 位置 | 字段 | 含义 |
| --- | --- | --- |
| 外层 | 重复字段 `1` | 消息节点 |
| 外层 | `2` | 标题 |
| 节点 | `1` | 原发送者 ID |
| 节点 | `2` | 秒级发送时间 |
| 节点 | `4` | 内容类型 |
| 节点 | `10` | 原会话 ID，不是原消息 ID |
| 节点 | `11` | 原发送者名称 |
| 节点 | `13` / `14` | 企业 ID / 企业名称 |
| 节点 | `101` | 富文本 |
| 节点 | `21` | 存在时保留无引用的回复正文 |
| 节点 | `17` 内的 `1002` | 引用证据 |

未解释的额外毫秒时间不替换节点字段 `2`。节点未提供原消息 ID 时，生成 `native:<载荷SHA-256>:<位置>` 本地键，保留 `original_message_id=null` 和 `message_id_basis=native_payload_position`。

原始作者 ID、企业、时间、节点哈希、父卡片 ID 和根消息 ID 分别保存。同秒记录按原生位置排序。引用按作者、秒级时间、原会话及去除展示 @ 的原文唯一匹配；引用节点作为证据，不重复计为聊天消息。

## 持久化与展示

`parent_id`、`root_message_id`、`nesting_depth`、`provenance_json` 通过增量迁移加入，不删除旧列。旧行默认无来源认证、深度为 `0`。迁移和实际导入前保留备份，并核对既有消息、问题、响应和游标。限定目标群的全量重放不推进账号全局游标。

`/api/wecom/report`、报告导出和看板共用去重问题口径，不受旧接口 500 条上限影响。限定子范围时附带 `ancestors` 证据，不额外计入当前消息总数。报告与页面递归隐藏凭据和手机号，原始 SQLite 证据保留在本地。

## 语义与统计口径

- 企业字段或姓名中的企业后缀决定主体，正文 @ 不改变归属。身份依据不足时标记 `unknown`。
- 件数、重量、体积、尺寸保留全部原文数组；未知项为 `null`，不猜币种、尺寸单位或规格。客户补充信息作为独立证据，不回填为原提问已有的字段。
- 同一询价的多个类别只计一个问题。相邻路线及规格补充按上下文关联，新路线或时效追问独立计数。
- “马上”“好的”等只算即时确认；价格、时效或明确处置边界才算方案。拒单属于有结论，不能据此认定承运或运输完成。
- 多路线提问只获得部分方案时，问题状态表示“已有相关方案”；`route_coverage` 分别列出有归属和未归属路线。一笔无地名价格不复制给全部路线。
- 首次确认、首条关联回复、首次方案、最后方案分别计时。首条关联回复可能包括客户补充信息，不能直接等同于客服响应时间。直接报价不补造确认时间，无 SLA 不自动标记超时。
- 使用最近开放问题等启发式规则时保留 `needs_review`。未被标记不代表已经人工审核，统计不能视为全部人工核准的 KPI。

32 个导出表头的详细解释见 [事件表字段说明](wecom-events-fields.md)。

## 验证与重放

在项目目录运行自动化回归：

```powershell
& '.\.venv\Scripts\python.exe' -m unittest discover -s tests -q
```

覆盖包括原生类型 `4`、12 层合成嵌套、截断载荷、引用去展示 @、多路线报价、补充信息与新追问、来源隔离、递归脱敏、快照 / WAL 和硬件调试器边界。测试通过仅证明对应代码行为；实际来源需另以解密结果、数据库完整性、原生载荷条数及哈希核验。合成嵌套测试深度不代表实际数据的嵌套层数。

已有有效 DPAPI 密钥时，可按目标群重放，无需重复调试：

```powershell
uv run chatlog-assistant wecom-local capture-once --account-id ACCOUNT_ID --full --conversation-name "目标群名称"
uv run chatlog-assistant wecom-local report --conversation-name "目标群名称" --output data/wecom-local/exports/target
uv run chatlog-assistant wecom-local serve --port 8766
```

看板可切换主群及全部转发或指定转发范围。每次处理的完整时间序列、路线表、人员企业表、核验结果和未获取范围，以对应本地交付报告为准。
